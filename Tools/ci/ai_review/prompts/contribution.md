## Contribution requirements (CI review only)

From `CONTRIBUTING.md`, `docs/en/contribute/code.md` and the PR template. Check each one; a gap is a finding of kind `process` about the PR as a whole, with a concrete ask.

- **Test evidence** (`CONTRIBUTING.md`, "Test your changes"). The PR states what was run and what it showed: a SITL scenario, a bench test, a flight log, or a test written to check the change. A bug fix shows the failure before the fix and its absence after, with the steps that reproduce it. Hardware-dependent changes need bench or flight evidence. Missing evidence is a concern; on flight-critical behavior (control, estimation, control allocation, failsafe and arming, navigation, actuator output) with no evidence of any kind it is a blocker. Name the evidence to provide and what it must show. Never ask for a test to be committed.
- **Committed tests** (`CONTRIBUTING.md`, "Test your changes"). A test added to the tree must guard behavior that is easy to break later and hard to notice otherwise, and must run fast with no real-time sleeps. A committed test that only re-checks this change, copies production logic into the test, or sleeps in real time is a finding: ask to drop it, or to keep only the part with lasting value.
- **Description matches the change.** The PR states the problem it solves (linked issue, `Fixes #N`), the solution, alternatives considered and how it was tested, with links to flight logs. Every behavior change and every affected vehicle type is stated; a description that understates scope is a finding.
- **Users who update.** New or changed parameters, defaults, uORB messages, MAVLink and logged topics, and any change in how a tuned vehicle responds need an upgrade note. User-visible changes need a `docs/en` update or a changelog entry.
