# Autotune response validation: comparison and evidence

## Conclusion

The proposed MC Autotune replaces acceptance based on RLS coefficient covariance
with an independent measurement of the proposed controller change.
It successfully tuned X500 in SITL, applied new PID gains after landing, preserved
all 15 audited parameters through a PX4 restart, and completed a subsequent hover.
The original implementation failed on yaw in three consecutive X500 runs in the
same environment. These are reproducible cases, not a fleet-wide failure rate.

This change trades a much longer experiment and additional memory for a check of
the candidate controller against measured vehicle response. Passing this check
does not establish optimal gains, universal stability, or better tracking in
every flight condition.

## Baseline and method

The baseline is unmodified upstream `3309f497d8fdb384f1f88cc2c989cf27286acb96`.
The proposed implementation is `c5411feeaf` with the simplification described
below. The flight-control sources in the baseline were not modified to reproduce
the failures. Both binaries used the same host, Gazebo models and test harness.

The comparison is end to end: the new implementation changes both excitation and
acceptance. It does not isolate the covariance threshold as the sole cause of
the difference. All review runs used simulation speed factor 4 unless stated
otherwise; durations below are simulation time.

`test/test_sitl_autotune.py` records the binary SHA-256, model and parameter
configuration, MAVLink acknowledgements, ULogs and before/after parameter values.
It requests Autotune through the MAVLink command used by QGC. A successful run
requires progress 95 before landing, unchanged gains before disarm, progress 100
after landing, finite changed P gains on all three axes, ordinary parameter
autosave, a full PX4 restart and a 60-second hover using the saved gains.
All 15 audited parameters are checked for persistence; this does not mean that
all 15 must change. In the X500 case, the nine PID values changed while the three
K multipliers and three attitude gains stayed unchanged.

## Shortcomings demonstrated in the original implementation

### X500 can fail despite completing roll and pitch identification

The original rule requires all five RLS covariance diagonal entries to be below
50, after at least five seconds on an axis. Each identification state has a
hard-coded 20-second timeout.

| X500 baseline run | Roll identification | Pitch identification | Yaw identification | Lowest observed maximum yaw covariance |
| --- | ---: | ---: | ---: | ---: |
| 1 | 4.992 s | 4.900 s | 19.980 s, failed | 1275.50 |
| 2 | 4.996 s | 4.992 s | 20.000 s, failed | 1292.09 |
| 3 | 4.904 s | 4.996 s | 20.000 s, failed | 1278.53 |

Durations span the first and last logged sample in each state; publication
intervals explain the apparent values slightly below five seconds.
Roll and pitch progressed normally. Yaw remained far above the threshold and
hit the state timeout. All three failures left the 15 parameters unchanged,
including after restart. These cases do not show a rollback defect by themselves.

Covariance describes uncertainty of the chosen model coefficients; it does not
directly measure whether replacing the controller is acceptable. Its numeric
scale also depends on regressor scaling and excitation. Substituting the FW
covariance rule or merely increasing 50 would not address that distinction.

### Slow vehicles need a time scale that firmware constants cannot provide

The original axis timeout cannot be adjusted through a parameter. The existing
`MC_AT_RISE_TIME` changes requested roll/pitch dynamics, while the original yaw
request remains fixed at 0.2 seconds.

The [PX4 tuning guide](https://docs.px4.io/main/en/config/autotune_mc) already
describes tuning large vehicles with a longer rise time. Therefore, claiming
that original PX4 cannot tune any large vehicle would be incorrect. The specific
limitation is its fixed experiment budget and acceptance rule, not mass alone.

The synthetic 1000 kg baseline run also reached yaw and timed out there after
19.988 seconds; its lowest logged maximum yaw covariance was 5140.95. It did not
produce or save a complete three-axis tune. The model has approximately
1049.6 kg m² roll/pitch body inertia and motor time constants of 0.2/0.3 seconds.
It is a stress model generated by `test/generate_autotune_models.py`, not a
validated representation of a particular 1000 kg aircraft.

### Model fitting is not an independent check of the replacement controller

Original MC Autotune computes GMVC gains from its identified model and checks
numeric gain bounds. It has no held-out response measurement of the controller
replacement. Optional in-air testing with `MC_AT_APPLY=2` starts after the new
gains are applied and checks control power for four seconds.

The new verifier can reject an aggressive attitude-gain proposal while accepting
its rate gains with the existing attitude loop. In the reviewed X500 run, the
full proposal had a response bound of -1.197 and was rejected; retaining the
attitude gains produced 0.482 and passed the same 0.2 threshold.

### Lifecycle bugs are separate from convergence

[Issue #28699](https://github.com/PX4/PX4-Autopilot/issues/28699) and
[PR #28700](https://github.com/PX4/PX4-Autopilot/pull/28700) cover completion after
landing, rollback on cancellation during an in-air test, and non-finite gains.
They do not establish the merit of a new convergence rule. Their regression
tests remain in this branch. Changing mode during active identification still
cancels Autotune; a later mode change cannot invalidate an already completed tune.

## What the new acceptance rule adds

1. Apply small multisine torque with the existing controller and measure the
   actual excitation, total torque, angular velocity and acceleration together
   in the rate loop.
2. Train the RLS/GMVC candidate during the first two periods, then freeze it.
   Measure four periods with each of two excitation phase patterns, with two
   settling periods per pattern. Verification samples do not update the candidate.
3. Use the measured transfer matrices to screen the proposed replacement,
   including axis coupling, the attitude loop, discrete PI and yaw filtering.
   Subtract an empirical allowance for repeat and phase disagreement.
4. Require low- and high-frequency coverage. Inadequate low-frequency coverage
   extends the period and repeats measurement within the same total timeout.
   Missing excitation, invalid samples or insufficient verification reject the
   tune. Excessive tilt or unsuccessful allocation reduce amplitude and restart
   the affected axis.
5. Try the full proposal, unchanged attitude gains, then half and quarter rate
   changes. Every option must pass the same response bound; a negligible change
   cannot count as successful tuning.

The detailed acceptance rule and parameter ranges are in [README.md](README.md).
The two-second axis pause is not the convergence criterion. With period `P`,
one complete measurement needs about `36 * P` seconds plus pauses: about five
minutes at the default 8 seconds, and 77 minutes at 128 seconds. `MC_AT_TIMEOUT`
is a total budget and must accommodate the chosen period and possible retries.

## Confirmed results and practical limits

| Scenario | Original PX4 | Proposed implementation |
| --- | --- | --- |
| Stock X500 | Yaw timeout in 3/3 runs; old gains preserved | Passed; saved gains survive restart and subsequent hover |
| Inertia ×4, motor lag 0.1/0.15 s | Yaw timeout; old gains preserved | Passed with period 32 s, timeout 1800 s, rise time 0.3 s |
| Synthetic 1000 kg | Yaw timeout; old gains preserved | Completed measurement, rejected by existing gain bounds; old gains preserved |

For the reviewed X500 run, roll P changed from 0.150000 to 0.127648, pitch P from
0.150000 to 0.128231 and yaw P from 0.200000 to 0.191160. The subsequent hover
had a maximum absolute roll/pitch angle of 0.344 degrees. This confirms a usable,
persistent tune in this case; it is not a tracking-performance comparison.

The slow model keeps X500 mass but multiplies inertia by four and increases motor
lag. Both versions used the same initial gains, filters and rise-time setting of
0.3 seconds. Original Autotune timed out on yaw at 19.980 seconds with a minimum
logged maximum covariance of 2315.61. The proposed version measured each axis for
approximately 386 seconds. It rejected the full proposal (bound -21.301) and the
full rate change with unchanged attitude gains (-0.203), then accepted half the
rate change (0.398). All nine PID values changed; all 15 audited parameters
survived restart. The subsequent hover's maximum absolute roll/pitch angle was
0.457 degrees. This establishes progress on slow, high-inertia dynamics; it does
not turn this 2.06 kg stress model into evidence of a successful 1000 kg tune.

The observer and lifecycle/VTOL suites pass 21 C++ tests. They cover a measured
small controller change, excessive attitude gains, missing excitation, noisy
measurements, missing periods, invalid configuration, repeated timestamps,
completion, cancellation, timeout, missing response, NaN handling and MC/FW
command ownership. They do not cover every combination of flexible structures,
delay, saturation, disturbance and operating point.

An accelerated 1000 kg run at speed factor 8, while another build was running,
was rejected on a 52 ms measurement gap. Its gains stayed unchanged. This
demonstrates a real tradeoff: rejecting unreliable samples can abort a tune under
host load. The guard was not relaxed to turn that run into a success.

The repeat at speed factor 4 used period 128 s, timeout 10000 s, rise time 2 s
and excitation strength 0.116667. It completed all three measurements, about
1538 seconds per axis, but failed the existing ideal-form D-gain limit of 0.1:
roll D was 0.154747 and pitch D 0.155743. Their parallel-form D values were
0.006841 and 0.006883. The response-bound check was not reached. All 15 parameters
remained unchanged after rejection. Longer measurement alone therefore does not
solve this case; extending the allowed gain range requires a separate argument,
not removal of a guard merely to obtain a successful run.

Other costs and restrictions that remain relevant to review:

- Approximately 35 KiB of observer heap storage and extra work to publish and
  analyse rate-loop measurements.
- Position-mode hover only; rate feedforward and battery torque scaling are
  currently rejected. This narrows the supported configurations compared with
  original Autotune. Attitude reference feedforward retains attitude gains.
- Empirical finite-frequency screening can miss behaviour between measured
  frequencies, outside the measured band or outside the tested operating point.
  Its uncertainty allowance is not a certified probability bound.
- Existing gain bounds still apply. A longer experiment does not guarantee
  acceptable GMVC gains or a successful 1000 kg tune.
- Conservative rejection can discard a usable controller; staged smaller gain
  changes can improve acceptance without delivering a faster response.
- Any parameter notification during measurement aborts the experiment, including
  a change unrelated to PID gains.

## Simplification

Removed the separate SITL-only response probe and torque-injection path, their
duplicate offline Python implementation and tests, and their second SITL harness.
The remaining harness exercises the production path. Also removed duplicate
cached-parameter comparisons, an unused callback wrapper and one redundant test.
The direct C++ observer tests and lifecycle/VTOL regression tests remain.

Parallel tests use separate PX4 instances, Gazebo partitions and private MAVLink
ports. A startup-script override suppresses the default UDP 14550 link, including
after restart, so tests do not appear in or receive commands from the user's QGC.

## Reproduction

Build each revision with `make px4_sitl_default`. Install `pymavlink` for the
harness. Use a fresh output directory and a distinct instance for each live run.

```sh
python3 test/test_sitl_autotune.py --binary /path/to/original/bin/px4 \
  --output /tmp/original-x500 --expect-failure --instance 73 --speed-factor 4
python3 test/test_sitl_autotune.py --binary build/px4_sitl_default/bin/px4 \
  --output /tmp/new-x500 --cancel-first --instance 73 --speed-factor 4
python3 test/generate_autotune_models.py --output /tmp/autotune-models
python3 test/test_sitl_autotune.py --output /tmp/new-slow \
  --model x500_slow --autostart 4001 --models-root /tmp/autotune-models \
  --param-file /tmp/autotune-models/x500_slow/initial-params.json \
  --param MC_AT_PERIOD=32 --param MC_AT_TIMEOUT=1800 --param MC_AT_RISE_TIME=0.3 \
  --instance 73 --speed-factor 4
python3 test/test_sitl_autotune.py --output /tmp/new-1000kg \
  --model x500_1000kg --autostart 4001 --models-root /tmp/autotune-models \
  --param-file /tmp/autotune-models/x500_1000kg/initial-params.json \
  --param MC_AT_PERIOD=128 --param MC_AT_TIMEOUT=10000 --param MC_AT_RISE_TIME=2 \
  --param MC_AT_SYSID_AMP=0.116667 --expect-failure --instance 73 --speed-factor 4
```
